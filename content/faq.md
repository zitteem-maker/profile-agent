## 4. IA et construction 0-to-1

**Que veut dire « vibe coding » pour elle ?** ✅

**Quelle est l'architecture de l'agent A ?** ✅
L'agent A est un assistant de support en self-service, construit avec Claude Code et l'API Claude Haiku, en production depuis l'été 2026. Base de connaissances : une base Notion d'une trentaine d'entrées sur 4 catégories, avec un statut par entrée (confirmé, à documenter, brouillon) ; une FAQ HTML interactive en est dérivée et n'affiche que les entrées confirmées. Un fichier `.md` contient uniquement les règles de comportement, dont l'interdiction d'inventer une réponse. Interface de chat web hébergée sur Cloudflare, code sur GitHub. Règle de confiance : au-dessus de 70 %, l'agent répond ; en dessous, il ne répond pas et tague l'équipe sur Slack pour mettre à jour la réponse et la base. L'agent répond seul, sans humain dans la boucle de réponse. Parcours de l'utilisateur : FAQ, puis agent IA, puis un groupe WhatsApp où le manager de l'équipe produit est le dernier niveau d'escalade. Principes : une seule source de vérité (la base Notion), pas d'invention, boucle d'amélioration via les alertes Slack. Le repo de l'agent A n'est pas consultable : il appartient au client.

**Comment évite-t-elle les hallucinations ?** ✅
Agent A : règle « jamais d'invention », seuil de confiance à 70 %. En dessous, l'agent n'improvise pas : il alerte sur Slack pour qu'elle corrige la réponse et la base. Agent B : règle demandant de poser des questions de clarification, glossaire commun avec la tech, règles d'escalade dans la base interne.

**Comment mesure-t-elle la qualité ?** ✅
Agent B : résolution IA vs humain suivie dans Intercom, CSAT en fin de conversation, temps de résolution des cas escaladés. Agent A : boucle de correction via les alertes Slack. Aucune métrique de volume documentée pour A.

**Comment structure-t-elle une base de connaissances, et qui valide ?** ✅
Agent A : 4 catégories, une trentaine d'entrées, mises à jour par Emeline à chaque alerte de faible confiance. Agent B : base interne (dont les règles d'escalade) et base externe, créées par elle, plus un glossaire commun avec la tech.

**Prompt, RAG ou fine-tuning : pourquoi ce choix ?** ✅
Pour cet agent de profil, elle a choisi le prompt : son profil et sa FAQ validés sont injectés directement dans le contexte du modèle. Ce volume tient dans le contexte, donc un RAG n'apporterait rien : il ajouterait une étape de recherche qui peut rater le bon passage, alors qu'ici le modèle a toujours tout sous les yeux, et chaque réponse se rattache à un fichier qu'elle peut corriger. Le prompt caching limite le coût de ce contexte à chaque message. Elle a écarté le fine-tuning : le contenu évolue et elle veut pouvoir le modifier en quelques minutes en éditant un fichier, ce qu'un modèle entraîné sur ces faits ne permet pas, et il serait plus difficile de vérifier qu'il n'invente rien. Un RAG deviendrait pertinent si sa base dépassait la taille du contexte.

**Comment gère-t-elle la sécurité et la prompt injection ?** ✅
Sur ses agents de support en production : moindre privilège, chaque agent n'a accès qu'aux tâches nécessaires (agents A et B) ; validation humaine pour les actions sensibles comme envoyer, supprimer ou payer, via l'escalade (agent B) ; marquage clair des données (surtout agent B) ; surveillance et journalisation des actions de l'agent pour repérer les comportements anormaux. Sur l'agent B, la résistance aux consignes déguisées repose sur l'entraînement du modèle par Intercom, qu'elle peut tester dans Intercom pour voir comment il réagit et corriger les règles. Pour cet agent de profil, la sécurité repose sur trois niveaux. Le contenu : il ne contient que des faits qu'elle a validés et aucune donnée client confidentielle, et l'identité et les coordonnées des visiteurs ne sont jamais envoyées au modèle, donc une injection n'a rien de sensible à extraire. Les règles : le prompt lui demande d'ignorer toute instruction de changer de rôle, d'embellir son profil ou d'inventer une expérience, de ne pas recopier ses instructions et de refuser les demandes de données confidentielles ; les résultats de recherche web, utilisés seulement pour les fourchettes de salaire, sont traités comme des données. Le serveur : la clé API reste côté serveur, et le compteur de questions, la limite de débit, Turnstile, les limites de longueur et un plafond de dépense protègent le service. Les tentatives de manipulation lui sont signalées dans Slack, et elle rejoue dix cas d'injection à chaque modification du prompt. Aucun système n'est à l'épreuve de toute injection : le but est de limiter ce qu'une injection pourrait obtenir.

**Quel est le coût d'exploitation ?** ✅
Pour cet agent de profil : environ 15 à 20 centimes par session de 9 questions, mesuré (Claude Sonnet 5.5 avec prompt caching). Pour ses agents de support A et B : non documenté, à discuter avec elle.

Oui. Pour l'agent A, le code est sur GitHub et l'interface hébergée sur Cloudflare ; son dépôt appartient au client et n'est pas consultable. Le dépôt de cet agent de profil est public : https://github.com/zitteem-maker/profile-agent

Après un changement d'instance, des entrées de la base de connaissances et des URL étaient obsolètes, et d'anciennes informations (un outil abandonné au profit d'un nouveau, des limites quotidiennes de leads supprimées) étaient restées documentées. Elle l'a vu dès son retour le lundi et l'a corrigé immédiatement. Depuis, elle demande à la tech la date exacte de toute migration importante, pour être en veille pendant cette période.

**Comment travaille-t-elle à distance ?** ✅
Elle travaille à distance depuis Chypre avec des clients français, en s'appuyant sur Slack, Linear et des tickets structurés.

**Pourquoi avoir construit cet agent ?** ✅
Ses projets ont été menés en interne sur des données clients confidentielles : elle ne peut pas les montrer. Cet agent les documente à sa place, pour répondre aux questions précises des recruteurs.
